# PRAVDA — план развития

**Статус:** действующая продуктовая спецификация

**Версия:** 0.3

**Дата:** 19 августа 2026 года

## 1. Назначение проекта

PRAVDA — большой сайт документальных статей об истории российско-украинского
конфликта, его правовых документах, политических решениях и конкурирующих
объяснениях. Читатель должен иметь возможность начать с даты, связи или номера
статьи, а затем получить один и тот же полный материал с проверяемыми ссылками.

Видео могут использоваться редакцией для поиска смысловых линий, а в дальнейшем
у каждой статьи может появиться собственный документальный выпуск. Исследовательское
видео не становится источником статьи автоматически: утверждения проверяются по
официальным документам и надёжным институциональным публикациям.

## 2. Одна публичная сущность

В публичном продукте существует только `ArticleRecord`.

- событие раскрывается внутри статьи;
- документ рассматривается внутри статьи;
- понятие объясняется внутри статьи;
- тезис и возражение сопоставляются внутри статьи;
- стрелка графа связывает две статьи, но не создаёт отдельный публичный материал.

У статьи есть стабильный строковый `id`, вычисляемый номер, дата хронологического
контекста, заголовок, краткое описание, развёрнутый текст, официальные источники и
переходы к другим статьям. Типы вроде `event`, `concept` и `argument`, теги,
служебная уверенность и происхождение редакционной заготовки читателю не показываются.

## 3. Три равноправных представления

Все представления импортируют один реестр `articlesData` и ведут на один маршрут
`/articles/:id`.

### Хроно

- размещает все статьи на шкале по `chronologyDate`;
- объединяет статьи одного календарного дня в читаемый кластер;
- показывает номер и название каждой статьи;
- не поддерживает отдельный массив «событий».

### Связи

- строит граф только из статей и `articleRelations`;
- позволяет найти любую статью и выбрать её центром текущего маршрута;
- показывает направление и редакционное объяснение связи;
- открывает ту же полную страницу статьи.

### Статьи

- показывает весь корпус в пронумерованном списке;
- поддерживает поиск по полному тексту;
- сортирует по номеру в обе стороны и по названию;
- сохраняет стабильный URL при изменении хронологической позиции и номера.

## 4. Редакционный стандарт статьи

Статья должна быть самостоятельным документальным материалом, а не расширенной
карточкой. Минимальная структура:

1. вводный текст, объясняющий вопрос и его место в общей истории;
2. четыре содержательных раздела минимум по два абзаца каждый;
3. фактический и правовой контекст;
4. конкурирующие трактовки без подмены позиции карикатурой;
5. границы вывода: что документы подтверждают и чего из них вывести нельзя;
6. ссылки на документы рядом с релевантным разделом и общий список источников;
7. осмысленные переходы к соседним статьям.

Текст не должен повторять один общий шаблон ради формального объёма. Каждый раздел
отвечает на конкретный вопрос статьи. Существующий корпус и новые статьи не должны
опускаться ниже проверяемого минимума в 400 слов в каждой языковой версии.

## 5. Источники

Приоритет источников:

1. тексты законов, договоров, резолюций и официальных решений;
2. публикации органов государства и международных организаций;
3. официальные наблюдательные и статистические отчёты;
4. архивная републикация, если первичный официальный документ иначе недоступен и
   статус републикации обозначен честно.

Официальная публикация доказывает принятие нормы, решения или позицию её автора,
но не делает каждую политическую оценку в документе универсально установленным
фактом. Закон, договор, декларация и мониторинговый отчёт выполняют разные
доказательные функции.

Inline-ссылка должна быть релевантна соседнему разделу. Нельзя механически
распределять общий список источников по абзацам. YouTube, транскрипты, внутренние
Markdown-файлы и реплики исследуемого говорящего не входят в публичные источники.

## 6. Работа с транскрибациями

Подробная процедура находится в `TRANSCRIPTION_PIPELINE.md`.

Транскрибации используются только как внутренний редакционный материал:

- восстановить смысловую линию и сильнейшую версию тезиса;
- найти уже существующую статью и дополнить её без дублирования;
- выделить вопросы, которые требуют проверки;
- проверить даты, нормы и факты по внешним документам;
- сохранить техническую воспроизводимость во внутреннем корпусе.

В публичном тексте запрещены имя исследуемого говорящего, `VIDEO_ID`, таймкоды,
фрагменты диалога, атрибуция «ответ/возражение», ASR-оговорки и показатели
уверенности расшифровки. Исследуемый говорящий не является участником, автором или
первичным источником проекта.

## 7. Языки

Публичный корпус поддерживает русский, английский и украинский языки. У каждой
статьи на всех трёх языках заполнены заголовок, краткое описание, вводный текст,
заголовки разделов и абзацы. Перевод должен сохранять доказательную осторожность,
а не только общий смысл.

## 8. Данные и маршруты

Основной публичный контракт находится в `src/domain/types.ts`:

```ts
interface ArticleRecord {
  id: string
  number: number
  title: Localized
  summary: Localized
  lead: Localized
  chronologyDate: string
  sections: ArticleSection[]
  sources: SourceLink[]
  links: ArticleLink[]
}
```

Номер не хранится как постоянный идентификатор: это позиция после сортировки по
дате. Добавление более раннего материала может изменить номера последующих
статей, но не их URL. `articleRelations` производятся из `ArticleLink` и обязаны
ссылаться только на существующие статьи. Изолированных статей быть не должно.

Старые структуры событий, узлов и аргументов допустимы только как внутренние
редакционные входы во время миграции. Представления сайта и AI-темы не должны
импортировать их напрямую.

## 9. AI-помощник

AI остаётся экспериментальным дополнительным режимом, а не отдельной моделью
контента. Он может распознавать тему разговора и предлагать читателю релевантные
статьи только через `articleIds`. Он не публикует сообщения, не говорит вместо
пользователя и не превращает живой разговор в публичный источник.

Технический протокол возможного realtime-бэкенда сохранён отдельно в
`AI_REALTIME_PROTOCOL.md`; он не определяет публичную модель сайта.

## 10. Проверки перед публикацией

Обязательный локальный pipeline:

```bash
npm run generate:data
npm run verify:data
npm test
npm run typecheck
npm run lint
npm run build
```

Проверки должны гарантировать:

- ровно один общий реестр и 85 уникальных статей в текущем корпусе;
- одинаковые идентификаторы во всех представлениях;
- валидные даты и автоматическую нумерацию;
- содержательный многоязычный объём;
- существующие endpoints всех связей и отсутствие изолированных статей;
- принадлежность inline-ссылок общему списку источников статьи;
- только HTTPS-источники без YouTube и внутренних транскриптов;
- отсутствие публичной атрибуции говорящему и служебных метаданных исследования.

Браузер импортирует только `src/data/articles.public.ts`. Его заранее создаёт
Node-side builder, поэтому legacy-реплики и технические ссылки не попадают в Vite
bundle. Финальный `verify:dist` повторно сканирует уже собранный артефакт.

После успешного pipeline изменения коммитятся и отправляются в `main`. Push
автоматически запускает сборку и публикацию GitHub Pages.

## 11. Ближайший редакционный план

1. Сохранять индивидуально развёрнутый текст всех 85 статей и не допускать
   возвращения общих редакционных шаблонов.
2. Проверять соответствие каждой inline-ссылки конкретному разделу.
3. Добавлять новые статьи только при появлении самостоятельного проверяемого
   вопроса, документа или события; повторы развивают существующую статью.
4. Для каждой будущей статьи готовить основу документального видео: вопрос,
   хронологию, документы, конкурирующие трактовки и границы вывода.
5. Расширять фильтрацию каталога по периоду и тематическому маршруту, не вводя
   публичные типы сущностей.
