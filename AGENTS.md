# AGENTS для PRAVDA

## Поведенческие правила для последующей работы в этом репозитории

- Любые изменения в коде/данных/контенте фиксируем как минимум одним commit в `main` и пушим в репозиторий.
- GitHub Pages деплоится автоматически по `push` в `main` через `.github/workflows/pages.yml`; отдельный ручной запрос на деплой не требуется.
- Перед публикацией изменения проходят pipeline: `generate:data` → `verify:data` → `test` → `typecheck` → `lint` → `build` → deploy.

## Операционный стандарт для новых сессий (чтобы не повторять ошибки)

1. Перед работой с проектом посмотреть:
   - `README.md` (структура и текущий статус)
   - `docs/CODEX_HANDOFF.md` (что уже в работе)
   - `docs/TRANSCRIPTION_PIPELINE.md` (обязательный конвейер видео)
   - этот `AGENTS.md` (обязательные правила для сессии)

2. При работе с видео в порядке приоритета фиксировать:
   1. `VIDEO_ID`, сырой источник транскрипта и таймкоды во внутренней исследовательской памяти.
   2. Ключевые смысловые линии, тезисы и сильные встречные позиции без подмены смысла.
   3. Какие существующие статьи уже раскрывают эти вопросы, чтобы дополнять их, а не дублировать.
   4. Какие официальные документы и государственные/международные источники подтверждают фактическую основу будущего текста.

3. После изменений всегда выполнять «один проход»:
   - обновить редакционные статьи/связи в `src/data/articleBuilder.ts` и файлах `src/data/articleEditorial*.ts`;
   - выполнить `npm run generate:data`, чтобы обновить чистую публичную проекцию `src/data/articles.public.ts`;
   - обновить `src/data/aiKnowledge.ts`, используя только `articleIds` (и при необходимости нейтральный демонстрационный текст `src/views/AIAssistantView.tsx`),
   - выполнить `npm run verify:data`, `npm test`, `npm run typecheck`, `npm run lint`, `npm run build`;
   - `git add ...`
   - `git commit`
   - `git push`

4. Не оставлять для следующей сессии неопределённости:
   - если видео дало новые смысловые линии или дополнения к статьям — сразу указывать их в памяти в формате шагов выше,
   - если не удалось завершить пайплайн, всё равно зафиксировать прогресс и точку остановки в handoff-доках.

## Стандартный порядок фиксации изменений после редактирования по видео

- Принять `VIDEO_ID`, сохранить канонический Markdown и локальный технический JSONL, чтобы потом можно было перепроверить смысл.
- Обновлять только релевантные статьи, их связи и ссылки AI на `articleIds`.
- После правок делается одно связное commit-сообщение, отражающее видео-источник и суть дополнений.
- Push в `main` = триггер автодеплоя; отдельный ручной деплой не планировать, пока нет специальной инструкции.
- Если видео-анализ повторяется в будущих сессиях, использовать тот же шаблон и не придумывать новый порядок.

- `transcripts/raw-youtube/` не изменяем: это резервный низкокачественный источник, а не основа анализа.
- Основную расшифровку делаем через `scripts/transcribe-multilingual.py`: локальный `faster-whisper` с полной моделью `large-v3`, исходное YouTube-аудио без повторного сжатия и фиксированный `language="ru"`, поскольку внутренний исследовательский корпус выделяет русскоязычные реплики Александра для восстановления нарратива. Флаг `--multilingual` оставляем для исключительных роликов, где важна украинская речь. Технические JSONL/TXT/метаданные храним в `.local/transcription-cache/`, а в `transcripts/` сохраняем только итоговый `VIDEO_ID.md`.
- `youtube-transcript.ai` допустим только как резерв для сверки; автоматически удаляем его дублирующиеся реплики и не подменяем им локальный транскрипт.
- Голоса размечаем как бинарную задачу: `Александр`, `Другой голос`, `Не уверен`. Личности меняющихся собеседников из чат-рулетки не устанавливаем.
- Локальный голосовой банк Александра заморожен по умолчанию: 108 подтвержденных
  примеров Александра и 20 чистых обезличенных отрицательных примеров. Новые ролики
  идентифицируем без постоянного обучения; временные `episodeSeeds` действуют только
  внутри одного ролика. Банк пополняем только при доказанном падении качества и
  только по подтвержденным человеком фрагментам. ONNX-модель, аудиоклипы и
  биометрические векторы храним только в `.local/` и не коммитим.
- Для старых, шумных и перебиваемых разговоров используем режим `--positive-only`: подтвержденные фрагменты Александра добавляем, а метки `Другой голос` не превращаем в отрицательные эталоны, поскольку в них может присутствовать наложившийся голос Александра.
- Сомнительные или смешанные фрагменты не приписываем Александру. Отрицательные примеры храним обезличенно и используем только для снижения ложных совпадений.
- Если пользователь задал диапазон из нескольких роликов, самостоятельно пройти
  весь диапазон и остановиться в его конце. Не требовать ручного подтверждения после
  каждого ролика и не создавать страницу разметки без признаков реального падения
  качества.
- Извлекаем смысловой нарратив и встречные позиции без подмены смысла, но используем их только как внутренний редакционный материал.
- Александр, `VIDEO_ID`, таймкоды, канонические транскрипты и ссылки на YouTube не являются публичными источниками и не должны появляться в тексте, метаданных или источниках статьи. Александр не связан с проектом и не атрибутируется как его автор или первичный источник.
- Любое фактическое или правовое утверждение в публичной статье проверяем по официальным HTTPS-источникам: ООН, международным организациям, государственным органам, текстам законов, договоров и решений.
- Публичная модель содержит одну сущность — `ArticleRecord`. Хроно, Связи и Статьи показывают один и тот же набор из 85 статей: соответственно на шкале времени, в графе и в пронумерованном списке. Все 85 материалов написаны индивидуально; общий шаблон или автоматически добавленный объём не считается развёрнутой статьёй.
- Новую тему не сохранять как отдельное «понятие», «событие» или «аргумент». Ею расширяется существующая статья либо создаётся полноценная новая статья с `chronologyDate`, содержательным вводным текстом, четырьмя разделами минимум по два абзаца, объёмом не менее 400 слов в каждой языковой версии, официальными источниками и связями с другими статьями.
- `src/data/articles.ts` — маленькая браузерная обёртка над сгенерированным чистым реестром `src/data/articles.public.ts`. Старые `EventRecord`, `KnowledgeNode` и `ArgumentRecord` допустимы только в Node-side `src/data/articleBuilder.ts` как временные редакционные входы и не должны попадать в Vite-граф импортов.
- После любой правки builder/editorial-данных обязательно запускать `npm run generate:data`. `verify:data` проверяет, что проекция не устарела, а `verify:dist` не допускает исследовательские имена, `VIDEO_ID`, YouTube и транскрипт-ссылки в опубликованном bundle.
- AI-темы ссылаются на материалы только единым массивом `articleIds`; отдельные `nodeIds`, `sourceEventIds` и `argumentIds` в публичной модели запрещены.
- Номер статьи не хранить вручную и не использовать в URL: это позиция после автоматической сортировки общего реестра по `chronologyDate`. Стабильный маршрут — `/articles/:id`.
- После изменений выполняем `npm run generate:data` → `npm run verify:data` → `npm test` → `npm run typecheck` → `npm run lint` → `npm run build`, затем `git add`, `git commit`, `git push`.

## Что считать обязательным к сохранению в памяти проекта

- Эта инструкция — рабочий ориентир для автоматизации, поэтому обновлять при смене пайплайна или методики обработки видео.
- Сначала проверять `README.md` и `docs/CODEX_HANDOFF.md` при handoff между сессиями.
